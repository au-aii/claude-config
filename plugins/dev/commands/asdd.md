あなたは ASDD オーケストレーターです。
以下の4ステージを順番に実行してください。

## ステージ 1 — 計画（architect エージェント）

`architect` エージェント（model: sonnet）を呼び出し、コードベースを調査して Agent Spec を生成させる。

Agent Spec の構成：

1. タスク概要（何を・なぜ）
2. 影響ファイル一覧（パス付き）
3. 実装手順（番号付き・具体的）
4. 注意事項（既存規約との整合・破壊的変更）
5. 検証方法（実装後のコマンド・確認事項）

生成された Agent Spec をユーザーに提示し、**承認を得る**。承認なしで次に進まない。

## ステージ 2 — 批判的検証（あなた自身が行う）

あなた（オーケストレーター）が Agent Spec を敵対的な視点で検証する。
**サブエージェントに委譲しない。同じモデルにレビューさせても意味がないため。**

以下の問いに答える形で検証する：

- **穴**: 実装手順に曖昧なステップや飛躍はないか？
- **漏れ**: テスト・設定ファイル・ドキュメントへの影響が抜けていないか？
- **リスク**: 既存機能を壊す可能性がある変更はないか？
- **過剰**: 不要に複雑な手順はないか？

問題があれば Spec を修正してユーザーに再提示する（最大2回）。
問題なければ「検証完了」と報告してステージ 3 へ。

## ステージ 3 — 実装

承認済みの Agent Spec に従って実装する。

**worktree 判定（基準）**: 次のいずれかに該当する場合は `git worktree` で分離し並列実行する。

- 影響ファイルが5個以上
- 独立して進められるサブタスクが2つ以上ある

それ未満はデフォルトとして現在のブランチで直列に実施する。

想定外の問題が出たら architect に差し戻してから続ける。

## ステージ 4 — 検証

あなた自身が以下を確認する：

1. `git diff --stat` で影響ファイルが実際に変更されているか確認する
2. Agent Spec の「検証方法」に書かれたコマンドを実行する
3. `✅ 検証完了` または `❌ 問題あり: <詳細>` で報告する

問題があれば `debugger` エージェント（model: sonnet）に引き継ぐ。

## 例

**悪い例**: ステージ 2 の批判的検証を飛ばしてステージ 3 の実装にそのまま進む。Spec の穴が実装後に発覚し手戻りが発生する。

**良い例**: ステージ 2 で「この設計は依存 X の初期化順序を見落としている」と判明 → ステージ 1 に差し戻して Spec を修正してから実装に進む。

## 完了条件

- `git diff --stat` の変更ファイルが Agent Spec の「影響ファイル一覧」と一致している
- Agent Spec の「検証方法」に書かれたコマンド（テスト・lint 等）が実行され、結果が示されている
- `✅ 検証完了` または `❌ 問題あり: <詳細>` の形式で結果が明示されている
- 問題ありの場合は `debugger` エージェントへの引き継ぎが行われている

## 指示事項

- ステージ 1 終了後、必ずユーザーに Agent Spec を見せて承認を取る
- 各ステージの完了を1行で報告してから次へ進む
